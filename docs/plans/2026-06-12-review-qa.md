## A. Orientation

**Q: What is DrugTree, architecturally?**
A dual-stack monorepo: a vanilla-JS atlas frontend and a FastAPI backend, sharing a canonical JSON data layer at the repo root. They talk only over HTTP. The frontend can run standalone against generated embeds (GitHub Pages), so the backend is optional at runtime.

**Q: What is the source of truth at runtime?**
The root `data/*.json` files — served by the backend's in-memory `DataSnapshotService`. SQLite (`drugtree.db`) is used **only** for the `targets` tables and is read-only at request time. ETL owns all writes to `data/`; `scripts/build_frontend_embeds.py` mirrors `data/` into `src/frontend/data/*.js`.

**Q: What was the developer last working on?**
A **two-pane workspace refactor**. The working tree shows: a sticky atlas (left) + scrollable workspace panel (right); a new context header (`#workspace-eyebrow/title/subtitle`); custom scroll controls (↑ / slider / ↓) synced via `syncWorkspaceScrollControls()`; orphan-only drug filtering (`orphanDrugIds`, `applySpecialDrugFilters()`); and migration of the drug detail view from a full-screen **modal** to an **anchored in-panel page** (`#drug-detail-page`, `positionDrugDetailOverlay()`). This refactor is **incomplete and uncommitted**.

## B. Frontend findings

**Q: How healthy is the frontend structure?**
Solid separation overall — stateless utilities (`app-state.js`), pub/sub stores (`selectionStore`, `graphStore`), D3 views, DOM-returning components, and an RDKit structure layer. The weak point is `js/app.js` (~2,760 lines): a god object holding boot, data loading, routing, filtering, rendering, and the detail surface. Extraction seams are already documented in `docs/ui/frontend-state-model.md` §8.

**Q: What's the biggest rendering inefficiency?**
`applyFilters()` couples the body-map update (B2) into every call, so each **search keystroke** triggers 14 × O(n) per-region drug-count passes even though search never changes the body map. Right behind it: `renderDrugList()` (B1) rebuilds the entire grid via `innerHTML` on every filter change, recreating up to ~120 cards and re-scheduling RDKit renders. The disease D3 tree (B8) fully rebuilds even when the region is unchanged.

**Q: Are there redundant render cascades?**
Yes. `clearFilters()` and its `handleSelectionCleared()` handler both fire several boundaries (double render). `handleRegionSelected()` runs the body-map update twice (explicitly, then again inside `applyFilters()`).

**Q: How does startup performance hold up given the data size?**
The embed payload is large (~9 MB of JS: `drugs-shell.js` 3.3 MB eager, `drugs.js` 4.3 MB lazy, `graph-nodes.js` 1.1 MB deferred). The shell + lazy-hydration + deferred-graph tiering is well-designed and keeps first paint reasonable, but the eager shell is still heavy and isn't served compressed in the static-host path.

**Q: Accessibility?**
Thin. Sparse `aria`, no focus trap or focus restoration on the detail page, no documented keyboard navigation beyond Escape, and the D3 trees aren't represented in the accessibility tree. The new `#drug-detail-page` needs `aria-modal`/focus management.

**Q: Mobile/touch?**
Functional down to 600px but desktop-first. Hover-dwell previews (1200 ms) have no touch equivalent, and the new anchored detail positioning assumes a desktop card rect.

**Q: Any dead code?**
`#modal-overlay` (index.html:347) is now vestigial after the detail-page migration; older modal-centric doc sections and any `body-map.js` remnants are stale.

## C. Backend findings

**Q: How healthy is the backend structure?**
Clean layering: routers → services → models → data. Routers validate with Pydantic and paginate most list endpoints. Services own caching and graph logic. The standout strength is the graph engine (`graph_index.py`): O(1) node/edge/family lookups, BFS neighborhoods, Kahn DAG validation, with `graph_queries.py` adding bucketed, version-hashed caching and hard result caps.

**Q: What's the most important runtime gotcha?**
The graph index is a **process-level singleton that never auto-invalidates**. After ETL updates `data/`, the served graph stays stale until a restart or an explicit `refresh()`. `DataSnapshotService` *does* check mtime/hash (24h TTL), so the two caches can diverge.

**Q: Any event-loop hazards?**
Yes — `routers/targets.py` opens **synchronous** `sqlite3` connections per request inside async routes (no pooling), and `GET /targets/{id}` issues three separate SELECTs (an N+1 shape). `db/connection.py` has async plumbing that this router doesn't use.

**Q: Pagination coverage?**
Mostly good, with gaps: `/drugs/search`, `/drugs/category/{c}`, `/diseases/search/{q}`, `/diseases/region/{r}`, and `/diseases/{id}/drugs` are unbounded; `/tree/disease/{id}` uses a non-standard hardcoded `[:20]` slice.

**Q: ETL state?**
Functional but carries debt: five files still use sync `requests` (`atc_orchestrator.py`, `drug_etl.py`, `fetch_atc_from_chembl.py`, `fetch_atc_from_kegg.py`, `atc_kegg_api_lookup.py`) against the `async`+`httpx` convention, and several modules exceed 1,000 lines.

**Q: Did anything in the old audit turn out to be already fixed?**
Yes. `docs/audits/current-implementation-audit.md` (2026-03-13) said `/health` reported a stale count from `drugs-full.json`; the current `main.py` derives `drugs_count` from `DataSnapshotService`, so that's resolved. Treat that audit as partially superseded.

## E. Cross-cutting risks (top of mind for the next round)

1. **Finish the two-pane refactor before optimizing on top of it** — half-migrated detail surface + lingering modal is a correctness risk.
2. **Graph-index staleness** (B1 backend) is a silent-wrong-data risk after ETL.
3. **Per-keystroke body-map recompute** (U1) is the single biggest cheap win on the UI side.
4. **Sync SQLite in async routes** (B2 backend) can stall the event loop under load.
5. **Doc drift** — keep `Architecture.md`/`UI-Architecture.md` updated as the refactor lands.

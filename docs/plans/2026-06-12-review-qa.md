## A. Orientation

**Q: What is DrugTree, architecturally?**
A dual-stack monorepo: a vanilla-JS atlas frontend and a FastAPI backend, sharing a canonical JSON data layer at the repo root. They talk only over HTTP. The frontend can run standalone against generated embeds (GitHub Pages), so the backend is optional at runtime.

**Q: What is the source of truth at runtime?**
The root `data/*.json` files — served by the backend's in-memory `DataSnapshotService`. SQLite (`drugtree.db`) is used **only** for the `targets` tables and is read-only at request time. ETL owns all writes to `data/`; `scripts/build_frontend_embeds.py` mirrors `data/` into `src/frontend/data/*.js`.

**Q: What was the developer last working on?**
A **two-pane workspace refactor** that has been carried forward into an optimization pass. The current working tree shows: a sticky atlas (left) + scrollable workspace panel (right); a context header (`#workspace-eyebrow/title/subtitle`); custom scroll controls synced via `syncWorkspaceScrollControls()`; orphan-only drug filtering (`orphanDrugIds`, `applySpecialDrugFilters()`); and an anchored in-panel detail page (`#drug-detail-page`, `positionDrugDetailOverlay()`). The old `#modal-overlay` DOM has been removed, though some method names (`showDrugModal()`, `closeModal()`) remain as compatibility wrappers.

## B. Frontend findings

**Q: How healthy is the frontend structure?**
Solid separation overall — stateless utilities (`app-state.js`), pub/sub stores (`selectionStore`, `graphStore`), D3 views, DOM-returning components, an RDKit structure layer, and focused controllers for preview, filters, atlas, and detail. `js/app.js` is still the largest frontend file, but it is down to 1,822 lines and now mainly orchestrates lifecycle/store events plus compatibility wrappers.

**Q: What's the biggest rendering inefficiency?**
At review time, `applyFilters()` coupled the body-map update (B2) into every call, so each **search keystroke** triggered 14 × O(n) per-region drug-count passes even though search never changes the body map. Current update: search is debounced and calls `applyFilters({ updateBodyMap: false })`; region counts are cached; mode switching preserves card DOM; `DrugGridRenderer` performs virtualized/windowed rendering for large visible sets; `DiseaseView.render()` uses a highlight-only path for unchanged signatures. Remaining high-value work is narrower state ownership rather than broad DOM replacement.

**Q: Are there redundant render cascades?**
Partly resolved. `handleRegionSelected()` no longer runs the body-map update twice, and `clearFilters()` now lets `SelectionStore`-backed clears flow through `handleSelectionCleared()` once. Some filter-chip paths still deserve a later diffing/dedup pass.

**Q: How does startup performance hold up given the data size?**
The embed payload is large, but the heaviest full-drug embed and graph bundles are no longer eager. Current measured payloads: `drugs-shell.js` 3.3 MB eager (497.7 KB gzip, 332.3 KB Brotli), `drugs.js` 4.2 MB lazy (722.4 KB gzip, 480.9 KB Brotli), `graph-nodes.js` 1.1 MB lazy (136.0 KB gzip, 108.0 KB Brotli). Remaining payload work is shell trimming and deployment-specific static-host compression config.

**Q: Accessibility?**
Core app a11y is better now: `#drug-detail-page` has dialog semantics, focus trap, and focus restoration; `#drug-grid` has list semantics; result counts are live; cards are keyboard-activatable; disease and genealogy D3 nodes have tree/treeitem roles and keyboard activation. Remaining gap: broader axe/manual screen-reader QA.

**Q: Does the Public/Scientist split expose the right evidence?**
Improved. Public mode no longer leaks raw SMILES/InChIKey through card attributes or fallbacks. Scientist mode hydrates full drug fields and now reads lineage edges from the lazy graph embed, preserving confidence, score breakdown, rationale/provenance, and explanation fields generated from `data/graph/edges/lineage.json`. The detail page shows lineage evidence text for graph-backed examples such as atorvastatin, and the visual snapshot flow waits for that evidence before capture. Chemistry descriptors not present in canonical data (cLogP/TPSA/HBA/HBD) remain absent rather than fabricated.

**Q: Mobile/touch?**
Functional down to a 390px viewport for the verified core flow. Hover-dwell previews now have touch equivalents for atlas regions and ATC tags; mobile detail placement is fixed within the viewport; the topbar no longer causes horizontal overflow. Full phone-flow UX polish is still future work.

**Q: Any dead code?**
The old `#modal-overlay` DOM is removed. Older modal-centric doc language has been updated in the current docs, and `DetailController` now owns the anchored detail page. Compatibility method names remain in `app.js` so existing call sites and tests keep working.

## C. Backend findings

**Q: How healthy is the backend structure?**
Clean layering: routers → services → models → data. Routers validate with Pydantic and paginate most list endpoints. Services own caching and graph logic. The standout strength is the graph engine (`graph_index.py`): O(1) node/edge/family lookups, BFS neighborhoods, Kahn DAG validation, with `graph_queries.py` adding bucketed, version-hashed caching and hard result caps.

**Q: What's the most important runtime gotcha?**
The graph index is a **process-level singleton**. Current update: startup warms `DataSnapshotService` + `GraphIndex`, `POST /api/v1/admin/refresh` refreshes the snapshot, graph index, and graph query caches, and graph lookup paths auto-refresh when source artifact mtime/size signatures change. Graph query caches include the graph source version.

**Q: Any event-loop hazards?**
Resolved for the current shape. `routers/targets.py` still uses local `sqlite3`, but the blocking work runs behind `run_in_threadpool()`. `GET /targets/{id}` now uses one compound helper/query path for target, drug edges, disease edges, and xrefs while preserving the response shape.

**Q: Pagination coverage?**
The reviewed gaps are now bounded: `/drugs/search`, `/drugs/category/{c}`, `/diseases/search/{q}`, `/diseases/region/{r}`, and `/diseases/{id}/drugs` take `limit`/`offset` with caps. `/tree/disease/{id}` uses explicit `limit`/`offset` instead of a hidden `[:20]` slice.

**Q: ETL state?**
Functional and materially more modular. The five formerly sync-`requests` files (`atc_orchestrator.py`, `drug_etl.py`, `fetch_atc_from_chembl.py`, `fetch_atc_from_kegg.py`, `atc_kegg_api_lookup.py`) have been migrated to `httpx`. The planned B7 split targets are now separated by stage: ATC lookup/enrichment/reporting, drug metadata/transform helpers, disease helpers/source loaders, and validation core/models. `graph_queries.py`, `audit_logger.py`, and `load_graph_edges.py` remain outside this plan's split scope.

**Q: Was the full ETL pipeline run?**
The real default full-source path was attempted with a 60-second timeout and stopped before writes. The launcher requires `data/processed/compound_master_table.tsv`, which is absent in this checkout; the script exited with its own "Input file not found" error before running drug ETL, external fetches, embed regeneration, or SQLite loading.

An isolated timed smoke was then run in a `/tmp` copy with a temporary compatibility table derived from canonical `data/drugs.json`: `ETL_CORE_TIMEOUT_SECONDS=120 ETL_STEP_TIMEOUT_SECONDS=5 timeout 240s bash src/backend/run_etl.sh --no-kegg --limit 20`. That smoke completed the launcher sequence, transformed 20 drugs with 0 skips, rebuilt graph/frontend artifacts, and loaded SQLite. Several optional source fetches degraded under the new timeout wrapper; DGIdb also returned current upstream schema/API errors, so source-specific freshness remains a follow-up.

**Q: Did anything in the old audit turn out to be already fixed?**
Yes. `docs/audits/current-implementation-audit.md` (2026-03-13) said `/health` reported a stale count from `drugs-full.json`; the current `main.py` derives `drugs_count` from `DataSnapshotService`, so that's resolved. Treat that audit as partially superseded.

## G. Responsive / auto-fit layout (user priority)

**Q: Does the UI auto-adjust to page size today?**
**Partially, with important gaps.** CSS has breakpoints at 1000 / 800 / 600 px (`style.css` §Responsive), but the core two-pane shell uses fixed minimum column widths:

```css
grid-template-columns: minmax(620px, 0.98fr) minmax(720px, 1.18fr);
```

Between ~1000–1340 px viewport width, the grid **overflows horizontally** (observed at 1200 px: columns want 1340 px, right pane clipped). Only at ≤1000 px does the layout stack to a single column.

**Q: What breaks on mobile (390 px)?**
- Atlas hero headline + summary pills + wrapped ATC chips fill the first ~980 px of scroll before the body SVG appears.
- Workspace stacks vertically; right panel height exceeded **27,000 px** (full drug list metadata in DOM + Disease Focus footer).
- Drug detail overlay covers most of the viewport; atlas is hidden behind it.
- Playwright covers a 390 px "core flow" but the full phone UX is not production-ready.

**Q: What should "auto-adjusted" mean for the next round?**
1. Fluid `fr`-based columns with no hard 620/720 px floor.
2. Container-aware D3 relayout (disease tree margins scale down).
3. Compact/collapsible atlas hero on narrow screens; body-first mobile layout.
4. Tabbed or accordion workspace sections to cap vertical scroll on mobile.
5. Topbar icon/overflow mode between 600–1000 px.

## I. Visual design / body atlas layout (user priority)

**Q: What is weak about the current body atlas layout?**
1. **Body is visually small** — capped at `min(344px, 100%)` inside a 396 px wrap; hero copy and summary pills consume vertical space above it.
2. **ATC side rails truncate labels** at moderate widths ("Respirat…", "Anti-infe…", "GU/E…").
3. **Constellation grid** (`grid-template-columns: 148px 1fr 148px`) squeezes the body between rails; connecting lines are decorative only.
4. **Region label pill** overlaps the lower torso; hover/lock feedback is good but easy to miss.
5. **Below 1000 px**, rails collapse to a chip grid (better), but the body drops below a long ATC list.

**Q: What would a better layout look like?**
Candidate directions (not mutually exclusive):
- **Body-dominant stage:** full-height SVG center, ATC as bottom chip strip or orbital ring.
- **Collapsible hero:** kicker + headline collapse to a single line after first interaction.
- **Region callouts:** inline labels on the SVG instead of distant side rails.
- **Workspace tabs:** Drugs | Disease graph | Detail — reduce duplicated headings and empty space in the right pane.

**Q: Disease graph visual issue?**
`DiseaseView` initializes at 1120 px width with 220 px left/right margins. In the actual ~580 px right pane, only ~140 px remains for horizontal tree spacing — the graph looks empty even when a11y treeitems are populated (Heart/Vascular → Hypertension → 4 drugs). This is a **layout bug**, not missing data.

**Q: Drug detail polish?**
Detail page works well: structure renders, Scientist mode adds class/MW/InChIKey/SMILES/genealogy. Public mode appropriately hides sensitive fields. `year_approved` shows "Unknown" for all inspected drugs — a data issue, not UI.

**Q: What data gaps did the browser expose?**

| `phase` | **100%** | Always shown (often "Phase IV") |
| `smiles` | **100%** | Structures render when RDKit loads |
| Disease–drug edges | **64 edges**, 36 unique drugs, 50 diseases | Disease view sparse outside demo clusters |
| Lineage edges | **50** | Genealogy thin for most drugs |

**Q: What should an agent supervision pass do?**
Correlate canonical `data/*.json` against web sources (openFDA, ChEMBL, KEGG, DrugBank/CTD, UniProt) with:
- Provenance tag per field (`source`, `url`, `fetched_at`, `confidence`)
- No silent overwrite of existing high-confidence values
- Human-review queue in `data/reports/` for conflicts
- Batch runner integrated into ETL (`agent_data_supervisor.py` — proposed in plan H6)

**Q: Priority enrichment order?**
1. `year_approved` — most visible "Unknown" in UI.
2. ATC placeholder resolution — 42.6% of drugs.
3. Disease–drug edge expansion — disease view usefulness.
4. Company/sponsor validation — trust issue when wrong.
5. Target/class/mechanism depth — Scientist mode value.

## L. Phase 4 implementation outcomes (2026-06-18)

**Q: What changed this round?**
All four Phase 4 tracks were implemented (see the plan's "Phase 4 — Implementation status"). Frontend: a fluid two-pane grid, a body-first atlas with a wrapping ATC chip strip, container-aware D3 sizing with content-driven disease-tree height, a collapsible hero, de-duplicated workspace chrome, and a full light theme with a persisted toggle. Backend: an opt-in agent-data-supervision ETL stage (`agent_data_supervisor.py`).

**Q: Which earlier risks are now resolved (K1–K6)?**
- **K1 (fixed grid overflow 1000–1340px)** — resolved: fluid `minmax(0,…)` columns; no horizontal overflow at 1440/1200/1000/800/390 (asserted).
- **K2 (disease graph invisible at real pane widths)** — resolved as a *layout* bug: margins/spacing scale with the container and the tree height is content-driven (removed the `Math.max(measuredHeight,…)` force + the CSS 640/760px floors). Remaining sparseness is a *data* gap (K5 → plan H3), not layout.
- **K3 (no light theme)** — resolved: `[data-theme]` token split + toggle + OS default.
- **K4 (body atlas secondary to marketing copy)** — resolved: body-dominant atlas, collapsible hero, ATC chip strip with full names.
- **K6 (mobile scroll budget)** — resolved: bounded mobile panel height → internal virtualized scroll; page height `< 6000px` (was ~27,000px).

**Q: What did the *visual snapshots* catch that green tests didn't?**
- The body SVG initially collapsed on mobile (a `height:100%`/`width:auto` chain with no definite box) — only visible in the PNG; fixed to a definite box.
- The disease tree "looked empty" even though `.node-disease` existed (passing the selector wait) — the PNG + node-coordinate dump showed forced-tall SVG whitespace; fixed.
- The light theme appeared to leave cards/detail dark — the PNG showed it; root causes were a transition-settle timing artifact (cards) plus a hardcoded dark detail-surface gradient (real, fixed with a light override).

**Q: Which risks remain?**
- **K5 (data gaps surface as "Unknown")** — the H pipeline is built and tested, but full-dataset enrichment coverage (year/ATC/edges/company/targets) needs a network-bound `--apply` run; canonical data is unchanged this round.
- **K7 (deployment compression)** and **K8 (broad a11y/axe pass, now including light-mode WCAG)** — still open.

**Q: Were any tests updated rather than just made to pass?**
Yes, one: `test_disease_interactions.mjs` asserted the removed fixed `min-height: 640px/760px` disease-view floors. Since visual evidence confirmed the new content-driven sizing is the intended fix, the test was updated to assert the content-driven contract (container min-height + no 760px svg floor + readable label size) rather than the stale pixel values. All other failures were fixed in product code, not tests.
